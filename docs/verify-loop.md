# Claude が自分でゲームを磨くための検証ループ

> 2026-09-04。判断の記録。
> 出てくる数字はすべてこのリポジトリで実際に走らせて取ったもの。

## 0. なぜ作ったか

既存のテスト212件は「**壊れていないか**」を守っている。よく出来ていて、速い（2.8秒）。
だがそこには**遊びの良し悪しが一切入らない**。

- 初見が13秒で死んでも、テストは緑
- 5秒間なにも起きない空白があっても、緑
- 1体だけ他の3倍手間取っても、緑
- 安い端末で30fpsまで落ちていても、緑

「面白いかどうかは人が遊ばないと分からない」——それは正しい。
だが**面白さの手前にある欠陥**には、人が要らないものが多い。
そこを人が来る前に潰すための装置を作った。

## 1. 三層

| | 何を見るか | 時間 | 依存 |
|---|---|---|---|
| `node --test` | 壊れていないか | **2.8秒** | ゼロ |
| `tools/sim/` | 遊びとして成立しているか | **約53秒** | ゼロ |
| `tools/probe/` | 実ブラウザでどう動くか | 約4分 | Playwright（`tools/probe/` の中だけ） |

入口は `node tools/verify.mjs`（1と2）、`--full` で3も。
**`src/` と出荷物は依存ゼロ・ビルド工程ゼロのまま。** npm は `tools/probe/` の外に出さない。

## 2. 一層目を作る前に踏んだ罠 —— 同じ種で結果が変わる

`test/headless.js` の `boot({seed})` は決定的、ということになっていた。実際は違った。

```
同一プロセスで seed 7 を、1面クリアまで2回:
  1回目 11,195歩 / 163,700点 / 残機1
  2回目  6,997歩 / 144,500点 / 残機2   ← 同じ種なのに違う

プロセスを分けて3回:
  3回とも 11,195歩 / 163,700点 / 残機1
```

`boot()` は動的 `import()` で `src/` を読む。**ES モジュールはプロセス内でキャッシュされる**ので、
2回目は `Math.random` を撒き直すだけで、セーブデータ・学習するボス・
ディレクター・ボス終盤の札の履歴は1回目のまま残る。

**`test/headless.test.js` の「同じ種は同じ結果になる」が通っていたのは、
そのテストがゲーム内1分しか回していないから。** 主張とコードがずれていた。

→ **1実行 = 1ワーカー**（`tools/sim/worker.mjs`）。使い回すと数字が静かに嘘になる。
両方のファイルに理由を書いた。

## 3. 一層目が出したもの（576本・53秒）

数字そのものは [sim-report.md](./sim-report.md)（自動生成）にある。読み方だけここに。

### 3.1 キャラの実測が、設計意図と合っていない

設計意図は「**後から開くキャラが強いわけではない。違うのはクセだけ**」で、
`test/balance.test.js` が `powerScore()`（式から出した解析値）を ±5% で縛っている。

実際に遊ばせると:

- 所要時間の中央値が **3.19倍** ひらく（🦍56.4秒 ↔ 🧑‍🌾180.1秒）
- 突破率が **0%〜67%**
- 命中率が **16%〜80%**

**ただしこれを「バランスが壊れている」と読むのは早い。**
測っているのは「**一つの決まった操縦のしかたで遊んだとき**」の成績で、
ボットは進行方向に対して横に狙いを合わせて撃つ。まっすぐ飛ぶ弾には向いていて、
広がる弾・曲がる弾には向いていない。人はそこを持ち替えるが、ボットは持ち替えない。

つまりこの数字が言えるのは
**「解析値では揃っているが、固定の操縦では揃わない」**まで。
どちらの読みが正しいかは、キャラごとに操縦を変えたボットを足せば分かる。**まだやっていない。**

### 3.2 初見は13秒で死ぬ。そして動いても変わらない

| ボット | 何を代表するか | 突破率 | 初回被弾までの中央値 |
|---|---|---:|---:|
| `hunter` | 狙って避ける | 29% | 40.6秒 |
| `dodge` | 避けるが狙わない | 6% | 15.1秒 |
| `sweep` | 往復するだけ | 0% | **13.5秒** |
| `idle` | 何も押さない | 0% | **13.6秒** |

**往復しているだけの `sweep` と、何も押さない `idle` が、ほぼ同じだけ生きる。**
最初の十数秒において、動くことに生存上の意味がほとんど無い、ということになる。
「触ってみたら分かる」を売りにするゲームで、ここは効いてくる可能性が高い。

### 3.3 6枚の札のうち1枚が一度も出ない

66回の抽選で観測されたのは5種類。`greed`（ボスが残ったベルを食う）が**0回**。
`src/engine.js:1242` が「盤面にベルが無いなら `greed` を除く」としていて、
ボス撃破の瞬間に盤面にベルが残っていることが、実際にはほとんど無い。

**一度も出ない札は、実質存在していない。**

### 3.4 動的難易度は飾りではなかった

`src/director.js` の `update()` を無効化して同じ条件で比べた（各80本）:

| | 突破率 | キャラ間の開き |
|---|---:|---:|
| ディレクター **生きている** | 21% | 3.82倍 |
| ディレクター **凍結** | 34% | 2.67倍 |

**上手いボットに対して13ポイント難しくしている。** 効いている。
ついでに、キャラ間の差を**広げる**方向にも効いていることが分かった。

### 3.5 時計の食い違い

`src/director.js` だけが `performance.now()`（実時間）で
「直近25秒の被弾」「直近20秒の撃破」を見ている。
ゲームの他の待ちは全部ゲーム内時間へ移されたあと（裏タブで止まるため）なので、
**ここだけが取り残されている**。

自動プレイは実時間の数百倍速で回るので、そのままだと窓が一度も閉じない。
ハーネスは既定でゲーム内時計を食わせる。`--wall-clock` で素の挙動も測れる。
（実測では集計への影響は小さかった: 突破率 29% vs 28%）

## 4. 二層目が出したもの —— 遅さの原因は JS ではなかった

CPU を 1/4 に絞る（安い Android の代わり）と、**p50 33.4ms = 30fps**、
33.3ms を超えるフレームが **78%**。このコンテナの素の CPU では 16.7ms 固定なので、
**速い機械で測っている限り一生見えない**。

原因の見当は最初、外れていた。疑ったのは
「敵1体ごとに毎フレーム `ctx.font` を組んで絵文字を `fillText` する」と
「必殺技のハンドラ14箇所が毎フレーム `enemies.filter()` する」だった。

CPU プロファイル（同じ絞り具合）:

```
87.9%  (program)          ← ブラウザのラスタ側。JS ではない
 2.7%  drawBackground     ← 一番重い JS 関数ですらこれだけ
 0.5%  update
 0.5%  fillText
```

毎フレーム作り直していたグラデーションをキャッシュしてみた → **70.2% → 72.9%**。
何も変わらなかったので、その変更は**入れていない**。

決めたのは、CPU を固定したまま**ピクセル数だけ半分にする**実験:

```
DPR 2 … p50 33.4ms / 33.3ms超え 78%
DPR 1 … p50 16.7ms / 33.3ms超え  0%
```

塗る量だけで決まっていた。`src/env.js` は DPR を一律 2 で止めていて、
それを払えない端末にも 2 を要求していた。
→ 追いつけていないときだけ 2 → 1.5 → 1 と**下げる**（戻さない）ようにした。
実測で 30fps → 60fps、遅いフレームは 78% → 27%。

**そしてこれは、ネイティブ化の判断にそのまま効く。**
Capacitor は同じ WebView で同じ raster を通るので、包んでも直らなかった。
→ [native-decision.md](./native-decision.md)

## 5. 三層目が見つけたもう一つ —— 起動が他人の CDN 任せだった

コールドスタート（開いてから遊べるまで）を測ったら **12,605ms** 出た。
内訳を取ると、犯人は1本だけだった。

```
commit 21ms / domReady 12,498ms / window.EDU 12,560ms / game 12,605ms

いちばん遅いリソース:
  12,443ms  css2?family=Baloo+2...   ← Google Fonts のスタイルシート
     29ms  diag.js
     27ms  save.js
```

`<link rel="stylesheet">` は**描画をブロックする**。だから third-party の CDN が
返ってくるまで、DOMContentLoaded ごと止まり、モジュールも読まれず、
ゲームは1行も動けない。

**12.4秒という数字自体はこの環境固有**（curl で叩くと 0.38秒で返る。
サンドボックスの proxy 越しに Chromium が読むと遅い）。
だが**形のほうは環境に依らない**: 起動の一本道に他人のサーバーが居る。
回線が悪い所でも、CDN が届かない所でも、同じ止まり方をする。

そのうえ `sw.js` は cross-origin を素通しする（そうしないと `api/` まで
巻き込む）ので、**この1本だけオフラインでキャッシュされていなかった**。
「PWA でオフライン対応」と言いながら、書体だけ毎回取りに行っていた。

→ Baloo 2 と Outfit の **latin サブセットだけ**を同梱した（どちらも可変フォントなので
2ファイル・計65KB）。どちらも SIL OFL で再配布できる。

```
12,605ms → 187ms
```

`test/sw.test.js` に4件足して縛った: 出荷される HTML が外部から何も読まないこと、
同梱した書体が app shell に入っていること、挙げたファイルが実在すること、
`fonts.css` が外部を参照していないこと。
`perf.spec.mjs` も、起動時の外部リソースが0件であることを見るようにした。

## 6. 三層目が確かめたもの

- app shell 37件がキャッシュされ、**回線を切っても起動して遊べる**（書体も含めて）
- `localStorage` が例外を投げる環境でも**起動して遊べる**（`src/save.js` の退避が実際に効いている）
- manifest はインストール可能条件を満たす
- 8ビューポート × 日英で、HTML で置かれた要素に画面外・重なり・小さすぎるボタンは無い

## 7. この装置に測れないこと（一番大事な節）

**面白さは測れない。** 上がるのは床であって天井ではない。

| 測れる | 測れない |
|---|---|
| 詰みが無い / 空白が無い / 例外が出ない | 楽しいか |
| 突破率・所要時間・命中率・死亡数 | 二度目を自分から始めるか |
| フレーム時間・メモリ・コールドスタート | 難易度が「気持ちいい」か |
| オフライン・保存の生存 | 人に見せたくなるか |
| HTML 要素の破綻 | **canvas に描かれたものの破綻** |

最後の行は特に正直に書いておく。このゲームの画面は**ほとんどが canvas** で、
題字もボタンの文字もキャラのカードも DOM には存在しない。
[layout.md](./layout.md) が記録した破綻（題字と説明文の重なり、カードの棒のはみ出し）は
**この装置では捕まえられない**。撮った画像は `tools/probe/shots/` に残るので、そこは人が見る。
機械で見るにはゲームが自分の描画矩形を外に出す必要があり、それは `src/` に手を入れる話。

そして [store-readiness.md](./store-readiness.md) が書いているとおり、
本当の関門は「**家庭の外の人が5人以上遊び、2回目を自分から始めるか**」で、
そこはコードでは動かない。この装置はその判定を**置き換えない**。

## 8. 次にやると効くこと

1. **キャラごとに操縦を変えるボット。** 3.1 の「バランスが壊れているのか、
   ボットが下手なだけか」は、これで決着する。
2. **`greed` の札が出る条件を見直す**（3.3）。
3. **最初の十数秒で、動くことに意味を持たせる**（3.2）。
4. **canvas の描画矩形を検査できるようにする**（7）。診断のときだけ出す形なら、
   出荷物を汚さずに済む。
