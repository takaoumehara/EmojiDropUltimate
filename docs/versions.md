# 版の一覧 — どれが「何人まで遊べる版」なのか

> 2人までの版と、4人の版が同時に世に出る。
> 「4人で入れない」という報告が来たとき、**どちらの話なのか**が分からないと
> 何ひとつ調べられないので、番号を振って両方を残す。

| 版 | 呼び名 | 同時に遊べる人数 | 印 | 状態 |
|---|---|---|---|---|
| **1.0** | **DUO(デュオ)** | ソロ / **ふたり** | `v1.0-duo` = `3f8946d` | **保存済み。消さない** |
| **2.0** | **PARTY(パーティ)** | ソロ / ふたり / **3〜4人** | v2.0 のブランチ | いまの版 |

起動時のスプラッシュに `v2.0 PARTY` と小さく出る。遊ぶ人が自分で答えられる。

---

## v1.0 DUO — 2人同時プレイまでの版(保存)

```
git checkout 3f8946d        # ← これが2人版の中身そのもの
```

**コミット `3f8946d` が v1.0 の実体。** v2.0 はこの上に積んであるので、
このコミットは履歴に残り続ける —— 番号さえ分かれば、いつでも戻れる。

`v1.0-duo` という**名前**を付けるのは、手元で1回だけ:

```
git tag -a v1.0-duo 3f8946d -m "v1.0 DUO — 2人同時プレイまでの版"
git push origin v1.0-duo
```

(この作業をした環境からはタグを push できなかったので、名前付けだけ残してある。
コミット番号で辿れる以上、失われたものは無い。)

**この版は消さない。** 4人の仕組みが実機で崩れたときに戻れる場所であり、
「2人プレイは前から動いていた」ことの証拠でもある。

### この版でできたこと

- ソロ
- **ふたり同時プレイ** — WebRTC の直結。あいことば6文字 / QR / 招待リンクで合流
- きずな、必殺技の合体、共有残機、共有ボスHP —— 2人ぶんの遊びは全部ここで完成している

### なぜ2人までだったのか

**4人ぶんのゲームコードは、この版にもう入っていた。**
`src/coop.js` の `peers` は最初から複数を持てるし、`test/coop.test.js` は
3人目・4人目が混ざらないことを確かめている。人数に応じた残機・ボスHP・
攻撃間隔の調整(`coopHpMul` 等)も入っている。

塞いでいたのは**繋ぎ方**ひとつだけだった。

- 直結は `RTCPeerConnection` を**1本しか張らない** → 相手はひとりまで
- 3人以上は中継サーバー(`server/`)経由が前提で、そのサーバーは
  **どこにも立っていなかった**(`index.html` の `coop-relay` が空)
- 立てると月額が発生する(→ [costs.md](./costs.md))ので、判断を保留していた

つまり「4人で遊べない」は、ゲームの問題ではなく**出会い方の問題**だった。

## v2.0 PARTY — 3〜4人が、サーバー無しで繋がる

### 何が変わったか

**中継サーバーを立てずに3〜4人が繋がるようにした。** 月額は今まで通りゼロ。

`v1` の思い込みは「直結 = 相手はひとり」だった。実際には
`RTCPeerConnection` を人数ぶん持てば**網目(mesh)**になる。
本当に足りなかったのは直結ではなく、**出会いの仕組みが2人ぶんの棚しか
持っていなかったこと**。そこを直した。

| | v1.0 DUO | v2.0 PARTY |
|---|---|---|
| ふたり | 直結1本 | 直結1本(**同じ。速さも変わらない**) |
| 3〜4人 | 中継サーバーが要る(未設置=遊べない) | **網目。サーバー不要** |
| 月額 | 0円 | **0円** |
| ホストが抜けたら | 世界が止まる | 残った中で**番号の若い人が引き継ぐ** |
| 満員 | — | 5人目にその場でそう伝える |

### 手を入れた場所

| ファイル | 何をしたか |
|---|---|
| `api/signal.js` | **部屋**(いま誰が居るか)と、**組ごとの棚**を足した。v1 が使っていた棚の名前はそのまま残してあるので、v1.0 のクライアントは同じ API で今まで通り繋がる |
| `src/mesh.js` | **新規。** 顔ぶれを見て、居る人ぶんだけ線を張る。申し込む側は「番号の若い方」と決め打ちにして、両者が同時に申し込む事故を消した |
| `src/ice.js` | **新規。** STUN/TURN の設定と候補集めを、直結と網目で共有(複製して片方だけ直す事故を防ぐ) |
| `src/coop.js` | 中継が設定されていなければ網目を使う。ホストが抜けたときの後継選び(`electHost`)を足した |
| `src/version.js` | **新規。** 版番号。スプラッシュとロビーの定員表示がここを読む |
| `src/render.js` | ロビーが定員(2 or 4)を経路から引くようにした。満員の案内を足した |

### 代わりに背負ったもの(正直に)

- **ホストの上りが人数ぶんになる。** 中継なら1通で済むワールド状態を、
  4人なら3通送る。実測 2,211 バイト × 15Hz × 3 ≒ **100KB/秒**。
  Wi-Fi と 4G/5G なら通るが、上りの細い回線ではここが最初に苦しくなる。
  軽くする手は分かっている(差分送信 → [multiplayer.md](./multiplayer.md))
- **線が1本失敗しても、その人だけが入れない。** 網目は組ごとに独立しているので、
  4人のうち1組だけ直通が張れない組み合わせがありうる
- **合図サーバーの命令数が増える。** ロビーにいる間、3秒ごとに顔ぶれを見に行く。
  始まったら15秒間隔に落とす

### 実ブラウザ4枚で確かめたこと(と、そこで出たバグ)

自動テストが通ることは「こちらが書いた段取りが正しい」ことしか証明しない。
**本物の Chromium 4枚・本物の WebRTC で動かした。** 中継サーバーは立てていない。

確かめられたこと:

- 4枚すべてが **4人**を認識し、**各自3本の線**(全体で6本)を張った
- ロビーの顔ぶれに4人の名前が並び、`START WITH 4` が出た
- **ホストのタブを閉じると、残った3人が全員同じ後継を選んだ**。
  ホストを名乗るのはきっかり1人で、それは残った中で番号が一番若い人だった
- 4回まわして、3回は **15秒**で全員そろった。1回は1組の握手が繰り返し失敗し、
  **張り直しで81秒かけて回復**した(下の3つ目のバグ)

**そして、自動テストでは絶対に出なかったバグが3つ出た。** どれも直してある。

1. **タブを閉じた相手に、誰も気づかなかった。** ホストが消えても引き継ぎが
   始まらず、全員の世界が止まったままになる。実測すると、Chromium は
   DataChannel の `onclose` を**永久に送ってこない**し、`iceConnectionState` は
   `disconnected` で止まって `failed` にならない。`connectionState` だけが
   約16秒後に `failed` になる。**ブラウザの通知は当てにできない。**
   → 自前の生存の合図(1.2秒ごと)が4.5秒途絶えたら死んだとみなす
2. **ロビーの顔ぶれが数秒で自分ひとりに戻っていた。** 名乗ったあと誰も何も
   送らないので、2.5秒で「音沙汰が無い」と判定されていた。中継経由でも
   同じだったはずの、古くからのバグ。→ 同じ生存の合図が塞いだ
3. **6組のうち1組だけが、永久に繋がらないことがあった。** 握手が止まった線を
   見張る仕組みが**握手が済んでから**動き出していたので、握手そのものが
   止まった線は誰にも見張られていなかった。→ 期限を「開通するまで」に掛け、
   失敗したら張り直す(最大5回)。一度読んだ合図を二度使わないようにもした
   —— 前回の合図を読むと、相手がもう捨てた接続に向かって握手を続けてしまう

### まだ確かめていないこと

**実機4台・携帯回線での4人プレイは、まだやっていない。**
ブラウザ4枚は同じ1台の中の話で、遅延も回線品質も、NAT の厳しさも現実とは違う。
特に「1組だけ直通が張れない」は、実際の携帯回線どうしで初めて本番になる。
→ [status.md](./status.md)

### 中継サーバーは捨てていない

`index.html` の `coop-relay` に URL を書けば、今まで通り中継が優先される。
網目で繋がらない組が実際に出たときの逃げ道として残してある。
どちらを使っているかはロビーの ⚡(直結・網目)/ 🛰(中継)で分かる。
