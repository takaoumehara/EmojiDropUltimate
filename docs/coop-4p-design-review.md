# もらったレポートは使えるか — EmojiDropUltimateに当てはめた査読

> 元ネタ: ユーザーが貼った「4人同期型モバイル・ウェブシューティングゲーム」市場・設計・技術レポート。
> 目的: このレポートの主張を鵜呑みにせず、実際のコード(`src/coop.js`, `server/`, `src/tether.js`, `src/director.js`, `docs/multiplayer.md` 等)と突き合わせて、**採用すべき部分・そのまま採用すると害になる部分・すでにやっている部分**を仕分ける。

## 結論から

レポートは**一般論としては正確**(業界で広く使われている知見の要約)。ただし対象にしている実例(CoD Mobile, PUBG Mobile, Soul Knight, Gunfire Reborn)は**すべて数十〜数百人規模のスタジオが作る、見知らぬ人同士のマッチメイキング前提のゲーム**。EmojiDropUltimateは**友達4人が合言葉/QRで集まる個人開発の協力シューティング**で、対象読者もサーバー予算も根本的に違う。

だから章ごとに扱いが変わる。

| 章 | 使えるか | 理由 |
|---|---|---|
| 1. 市場分類 | 参考程度 | どのタイトルも「見知らぬ人との対戦・マッチメイキング」前提。このゲームは友達だけの協力なので、分類自体があまり当てはまらない |
| 2〜3. ゲームデザインパターン | **大部分そのまま使える** | ジャンルが違っても「相互依存」「緊張と緩和」「非言語コミュニケーション」は普遍的な原則 |
| 4. 技術アーキテクチャ(Colyseus/オーソリテイティブサーバー) | **このゲームには不採用が正しい** | 理由は下記。しかも `docs/multiplayer.md` で**この判断はすでに一度やっている** |
| 5. 推奨仕様 | 一部採用・一部規模不一致 | 8〜12分セッション、正のフィードバック演出は使える。ボイスチャット・空間ピンは過剰投資 |

---

## 1. 技術アーキテクチャ章 — レポートの推奨をそのまま採用してはいけない理由

レポートは「クライアント間直結(P2P)ではなくオーソリテイティブサーバー(Colyseus等)が不可欠」と書いている。**これは対戦ゲーム(PvP)や見知らぬ人とのマッチングが前提の議論であり、このゲームには当てはまらない。**

根拠は3つ、すべて `docs/multiplayer.md` に本人がすでに書いている。

1. **不正対策が要らない。** オーソリテイティブサーバーが必要な最大の理由は「クライアントが自己申告する位置・ダメージを信用できない(チートされる)」から。このゲームは友達同士の協力プレイで、対戦相手を負かすための不正インセンティブがない。唯一の懸念はスコア共有機能(`sharecard.js`)の見栄えだが、これはサーバー権威化ではなく別の対策(スコア送信時の簡易検証)で足りる規模の話
2. **常駐サーバーはホストに一律の遅延を強制する。** いま採用しているホスト権威モデルは「ホストだけ遅延ゼロ、ゲストに遅延がある」という不公平を抱えているが、専用サーバーに変えると**全員が往復遅延を負う**(東京リージョンが無いサービスだと悪化することは`docs/multiplayer.md`で実測済み)。友達内の持ち回りホストで十分な規模なら、後者のほうが体感は悪くなる
3. **費用と運用がゼロで済む設計をすでに達成している。** `server/`は依存パッケージゼロで動き、リレーを立てなくてもP2Pだけで遊べる。Colyseusに乗り換えると常時起動のNodeプロセスと運用コストが発生し、「サーバーを立てない選択」という今の強みが消える

**すでに実装済みで、レポートが挙げる「遅延隠蔽の3点セット」もほぼ揃っている**(クライアント予測・サーバー再調整に相当するもの):
- ホストは15Hzでワールドスナップショットを送信、ゲストは60fpsへ補間して描画(エンティティ補間に相当)
- 自機の位置は各クライアントがローカルで即時反映(クライアント予測に相当。信頼できる相手なので巻き戻し処理までは不要)

**唯一、本当に足りないのはレポートの「差分エンコーディング」に相当する部分。** 今は毎回フルスナップショットを送っている。これは`docs/multiplayer.md`にも「圧縮(permessage-deflate)は意図的に後回しにした」と明記された**既知の次の課題**。4人に増やして帯域が気になったら、まずここに手を入れるのが正しい優先順位。**Colyseus導入より先にやることはこっち。**

**技術スタック比較表(ネイティブ vs Web)は無関係。** このゲームはブラウザ完結・Capacitorでのストア配布方針(`docs/native-options.md`)がすでに決まっており、Unity/Photonへの乗り換えは検討事項にすらならない。

## 2. ゲームデザインパターン章 — ここは実際に効く

### 2.1 相互依存性・非対称役割 → 部分的にすでにある、拡張の余地あり

レポートの「キャリー問題」(1人が全部倒して他3人が受動的になる)への対処として、タンク/DPS/サポートのような固定クラス制を提案している。

このゲームは16キャラクターが「弾の飛び方」で差別化されており(まっすぐ/追尾/貫通/大きいが近距離、など)、固定ロールではなく**プレイスタイルの違い**で個性を出す設計になっている(`config.js`のコメント: 「強い癖には必ず埋め合わせを付ける」)。さらに`tether.js`の「きずな」が**1人では絶対に成立しない相互依存**をすでに作っている。

固定クラス制を今から追加するのは推奨しない。理由は前回の回答でも触れた原則: **「同じ見た目で違う役割は最も混乱する構成」**。今の16キャラは見た目も個性も違うが役割は対称なので、そこに非対称ロールを重ねると、「なぜこのキャラだけ回復できるのか」を説明なしで伝える追加コストが発生する。

**代わりに使える方向性(低コストで同じ効果)**: きずな(tether)の「参加順の数珠つなぎ」を活かし、**鎖の位置によって効果を変える**(両端は攻撃、中継は防御、など)。キャラクターを増やさずに、その場の並び順という一時的な状態で役割が生まれるので、覚える負荷がゼロで済む。

### 2.2 危機と救済(ノックダウン→蘇生) → 未実装、追加する価値が高い

現状は「残機はチーム共有・誰かが被弾すると即座にチームの残機が1減って0.5秒後に復帰」という設計。**ドラマが起きる余地がない**——誰が倒れたか、誰が助けたかが可視化されないまま数字が減るだけ。

これはレポートの指摘が正しく刺さる箇所。**P1で追加を推奨**: 被弾した瞬間は即死亡・即残機減にせず、一定時間(3〜5秒)「ダウン状態」にして、他プレイヤーが近づく(あるいは、きずなの線が触れる)ことで復帰できるようにする。誰も助けられなければそこで残機が減る。これだけで「絶望からの逆転」が起きる余地が生まれ、4人プレイならではの緊張が増える。

ただし範囲だけ注意: 全滅間際の無敵シールド演出のような「過剰な救済演出」は、ボス側にすでにある `LAST_STANDS`(revive/split/flee/greed/legacy/turn)という**敵側の土壇場ギミック**と役割が被らないようにする。プレイヤー側の劇的演出とボス側の劇的演出が同時に起きると読み合いが破綻する。

### 2.3 緊張と緩和(AIディレクター) → すでに実装済み、コンセプトは正しい

驚いたことに、レポートが提案している「AIディレクターの思想に基づく緊張度制御」は**すでに`director.js`として実装されている**。命中率・撃破ペース・被弾を見て、湧き数・攻撃頻度・支援ベル頻度を動的に調整する仕組みがある。これはLeft 4 Deadの director と同じ発想で、レポートの指摘は正しいがすでに手当て済み。

**4人プレイで確認すべき点(P1)**: 今のdirectorは`game.stats`という単一の集計を見ている。4人プレイで1人が上手くて3人が苦戦している場合、平均や合算の取り方次第では「全体的には順調」と誤判定し、苦戦している3人への支援ベルが減ってしまう可能性がある。**個人ではなく最も苦戦しているプレイヤーを基準にする**(ワーストケースドリブン)方が、レポートが警告する「上級者が全部持っていく」問題への対処として直接効く。

### 2.4 空間ボイスチャット・ピンシステム → このゲームの規模には過剰投資、P2

友達4人が同じ部屋にいるか、Discord等の外部ボイスチャットを使っている前提が強いカジュアルゲームで、ゲーム内蔵の距離減衰ボイスチャットを実装する投資対効果は低い。実装コストも高い(WebRTCの音声トラック管理、モバイルでのマイク権限、エコー処理)。

**代わりに、きずなの視覚エフェクトがすでに非言語コミュニケーションの役割を部分的に担っている。** ここを強化する方が安い。例えば「相方が助けを必要としている」状態(残機1・ダウン寸前)を画面越しに視覚的に伝える演出を足す方が、ボイスチャット実装よりずっと低コストで同じ効果に近づく。

### 2.5 プライベートドロップ / 共有バフ → 該当なし

このゲームにはアイテムドロップやルート分配の概念がない(スコア制・共有残機制)。レポートのこの節は適用対象がない。

## 3. 優先度まとめ

| 項目 | 優先度 | 理由 |
|---|---|---|
| 中継サーバーのデプロイ + `coop-relay` meta設定 | **P0** | 4人プレイ自体がこれをしないと有効化されない(前回の回答の繰り返し) |
| ダウン→蘇生の導入(2.2) | **P1** | 4人プレイのドラマ性を最も安く底上げできる |
| Directorをワーストケース基準に(2.3) | **P1** | 4人化で「上級者1人が指標を歪める」リスクが実際に発生する |
| スナップショットの差分/圧縮送信 | **P1** | レポートが正しく指摘した数少ない技術的ギャップ。Colyseus導入ではなくここ |
| きずなの鎖に位置依存の効果を足す(2.1) | **P2** | 効果は見込めるが、まずP0/P1をやってから |
| 苦戦シグナルの視覚化(2.4) | **P2** | ボイスチャットの安い代替。余裕があれば |
| Colyseus/オーソリテイティブサーバーへの移行 | **不採用** | このゲームの規模・信頼モデルには合わない。理由は§1 |
| 距離減衰ボイスチャット・空間ピン | **不採用(将来の検討事項)** | 投資対効果が低い。友達内プレイならDiscordで代替可能 |

## 4. 検証方法

数値やレポートの主張を信じるだけでなく、実際に4人でプレイして次を観測してください。

- ダウン→蘇生を入れた場合: 「4人プレイ10回中、意図的に仲間を助けに行く行動が発生した回数」を記録する。毎回起きるなら効いている
- Directorのワーストケース化: 「腕前差が大きい4人パーティで、苦戦している人にも支援ベルが十分な頻度で出るか」を、既存の`game.stats`ログと突き合わせて確認する
- 差分圧縮導入後: `server/relay.js`の実測(4人で106KB/秒)がどれだけ下がるかを測る
