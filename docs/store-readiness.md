# ストア提出の準備状況 — 実測にもとづく評価

> 2026-07 時点。感覚ではなく、リポジトリを実際に調べた結果に基づく。
> 数字は「良く見せる」ためではなく「次に何をやるか決める」ために付けている。

## 1. 点数(領域別)

| 領域 | 点 | 根拠(実測) |
|---|---:|---|
| 技術基盤 | **85** | 外部依存ゼロ・オフライン動作・テスト73件全通過・弾180発で60fps・P2P同期はブラウザ2枚で検証済み |
| 見た目 / 視認性 | **78** | セーフエリアは iPhone 15 Pro / 17 / SE の実寸で検証。弾の可読性は18px下限を実測で決定。ただしキャラカードUIは作ったばかりで実機未検証 |
| ゲーム設計 | **65** | 16体に実測で異なる弾道、ボス復活+突進、ベル経済、救済ベル。ただし難度調整は毎回作り直しており、まだ落ち着いていない |
| **面白さの証明** | **20** | **第三者が一人も遊んでいない**。フィードバックは作者と子供の2人だけ |
| 製品としての足回り | **35** | エラー報告なし・計測なし・プライバシーポリシーなし・シグナリングAPIにレート制限なし |
| ストア提出の準備 | **15** | 必須書類が未整備。加えて Apple 4.2 のリスクが未解消 |

**総合**
- **Webの作品 / ポートフォリオとして: 78点** — この用途なら今すぐ人に見せてよい。
- **ストアに出す製品として: 35点** — 出せない。理由はコード品質ではなく、下の 3 と 4。

## 2. いま一番のリスクは「位置情報」

`src/weather.js` が `navigator.geolocation.getCurrentPosition()` で**端末の正確なGPS座標**を取得し、
それを**第三者のAPI2社**へ送っている。

- `api.bigdatacloud.net`(逆ジオコーディング=座標→都市名)
- `api.open-meteo.com`(天気)

天気連動は良い機能だが、**子供が遊ぶゲームで正確な位置を外部に送るのは、ストアでは重い扱いになる**。
Apple の Kids Category と Google Play の Families ポリシーはどちらも、児童からの位置情報収集を強く制限する。
提出時のプライバシー申告でも「正確な位置情報」「第三者への送信」を申告することになる。

**対応(軽い順)**
1. 位置を使うのをやめ、**IPベースの粗い地域**か、**プレイヤーが都市を選ぶ**方式にする(推奨)
2. 位置を使うが、**初回に理由を説明して同意を取る**+ 座標を**小数点1桁に丸めて**送る(約11km精度)
3. 天気連動を任意機能にして、既定はオフ

## 3. ストアに出せない実務的な理由

コードとは別に、**提出そのものに必要なもの**が揃っていない。

| 必須 | 状態 |
|---|---|
| プライバシーポリシー(URL) | **無い**。Apple も Google も全アプリで必須 |
| プライバシー申告 / データセーフティ | 未作成。位置・端末ID・スコア送信の申告が要る |
| 年齢レーティング | 未取得 |
| LICENSE | **無い** |
| アイコン各サイズ・スクリーンショット・プレビュー | PWA用4枚のみ。ストア規定のサイズは未作成 |
| サポート窓口(URL/メール) | 未設定 |

## 4. Apple 固有の構造リスク(4.2 Minimum Functionality)

**Web を WKWebView で包んだだけのアプリは、Apple に落とされる可能性が高い。**
「サイトを束ねただけ」と判断されるとリジェクトされる(ガイドライン 4.2)。

現実的な道は3つ。

| 道 | 労力 | リジェクト危険度 | 備考 |
|---|---|---|---|
| **A. Web / PWA のまま** | ゼロ | 無し | ホーム画面追加で全機能が動く。**いま最も理にかなっている** |
| **B. Capacitor 等で包み、ネイティブ機能を実装** | 中 | 中 | Game Center・課金・触覚・プッシュ・完全オフラインを本気で足せば通る例は多い。「包むだけ」だと落ちる |
| **C. ネイティブ or ゲームエンジンへ移植** | 大 | 低 | 一番確実だが、今の資産(5,900行のJS)をほぼ書き直す |

**Google Play は事情が違い**、TWA / WebView 方式が通常どおり受理される。
つまり**Android だけ先に出すことは現実的**で、Apple より判断が早い。

## 5. 出す前にやるべきこと(優先順)

### 最優先 — これをやらずに出す意味がない
1. **第三者に5人以上遊ばせる。** 判定基準は一つだけ:「言われなくても2回目を始めるか」。
   これまでの指摘(弾が見えない/簡単すぎる/輪が変/同期バグ)は全て身内から出た。
   まだ出ていない問題が同じ密度で残っていると考えるのが自然。
2. **エラー報告を入れる。** 現状 `onerror` も `unhandledrejection` も**1件も無い**。
   自分の持っていない端末で落ちても、永久に気づけない。
3. **最低限の計測。** 「起動→2回目のプレイに進んだ割合」だけでいい。
   これが無いと 1 の判定が主観のままになる。

### 出すと決めたら必須
4. 位置情報の扱いを 2 のとおり変更
5. プライバシーポリシー・データセーフティ申告・年齢レーティング・LICENSE
6. `api/signal` に**レート制限**(現状ゼロ)。無いと第三者に叩かれて KV の枠と費用が飛ぶ
7. アイコン・スクリーンショット一式

### 品質として足りていないもの
8. **難易度設定**。いまは Director が自動調整するだけで、明示の「やさしい」が無い。子供に渡すなら要る
9. **アクセシビリティ**: `prefers-reduced-motion` 未対応、色覚特性への配慮なし、音量は ON/OFF のみ
10. **対応言語が日英2つ**。ストアで広げるなら増やす
11. **初回の遊び方の導入**。いまは短いテキストのみ

## 6. 結論

**技術的には出せる水準にある。出せない理由は「面白いという証拠が無い」ことと「提出書類が無い」こと。**

順番としては —
1. まず **Web のまま**、第三者に遊ばせて「2回目を遊ぶか」を確かめる
2. 遊ぶなら **Android(TWA)から**出す。Apple より速く、判断材料が得られる
3. Android で数字が付いてから **iOS**。その時に B か C かを、実際の利用数を見て決める

いま iOS に突っ込むのは、**一番労力が大きく、一番リジェクトされやすく、一番学びが少ない**選択になる。
