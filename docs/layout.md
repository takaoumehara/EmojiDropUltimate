# 画面の作り — 「遊ぶ板」と、縦が短い端末

> 判断の記録。数字はすべて Playwright での実測(11ビューポート × 13画面 × 日英)。

## 1. 何が起きていたか

全画面を全ビューポートで撮って並べたら、**電話の縦持ち以外がほぼ全部おかしかった**。

### 横に広い画面(デスクトップ)

窓いっぱいが盤面になっていた。1920×1080 で測った結果:

| | 電話 (393px) | デスクトップ (1920px) |
|---|---|---|
| 自機の大きさ / 盤面の幅 | **10%** | **2%** |
| 敵の湧く幅 | 393px | 1920px |
| 端に湧いた敵までの距離 | 約 200px | **約 700px** |

見た目が寂しいという話ではない。**届く前に画面を抜けていくので、同じゲームではなくなっていた。**
HUD も左上と右上が 1900px 離れ、視線が一度に入らない。

### 縦が短い画面(電話の横持ち・852×393)

- 題字と説明文が重なる
- **4つのボタンすべて**で、主文と副文が重なる
- キャラのカードで、5本の数値の棒が**カードの枠の外にはみ出し**、
  ページ点と「← スワイプ →」と READY ボタンに重なる
- ふたりで遊ぶロビーは**下端で切れて、最後のボタンが押せない**

原因は UI 倍率の底上げだった。

```js
UI = Math.max(1.05, Math.min(W / 380, H / 680, 1.6));
```

`1.05` の底上げは「幅の狭い端末で字が小さくなりすぎない」ためのもの。
ところが 852×393 では素の値が 0.578 なので、**倍率だけが 1.8 倍に持ち上がり、
行間は H に比例して詰まったまま**になる。結果、字は大きく行間は狭く、全部が重なった。
読めないほうが小さいより悪い。

## 2. どう直したか

### 遊ぶ板(`src/env.js`)

`W` / `H` を「窓の大きさ」から **「遊ぶ板の大きさ」** に変えた。板は縦長で、窓の中央に置く。

```js
export const STAGE_MAX_W = 560;      // 電話の幅(393〜430)を大きく超えない
export const STAGE_MIN_ASPECT = 0.45; // 縦に長い画面で糸にならない下限

export function stageSize(winW, winH) {
  const w = Math.min(winW, STAGE_MAX_W);
  const h = Math.min(winH, w / STAGE_MIN_ASPECT);
  return { w, h };
}
```

| 窓 | 板 | 電話と同じか |
|---|---|---|
| 360×640 / 375×553 / 393×665 / 393×852 / 430×932 | そのまま | **完全に同じ** |
| 852×393(横持ち) | 560×393 | 中央に寄る |
| 768×1024(iPad) | 560×1024 | 中央に寄る |
| 1440×900 | 560×900 | 中央に寄る |
| 1920×1080 | 560×1080 | 中央に寄る |
| 2560×1080 | 560×1080 | 中央に寄る |

描画側は**1行も変えていない**。`ctx.setTransform` で原点を板の左上にずらすだけで、
既存の `W` / `H` を使ったコードがそのまま板の中に収まる。板の外は飾りの帯で、
真っ黒だと「読み込みに失敗した画面」に見えるので、板の後ろに淡い光を置いた。

板の外へ弾や演出が漏れないよう、描く前に板で切り抜く(`ctx.clip`)。

### 指の位置(`src/input.js`)

指の座標は窓のもの、ボタンは板のもの。**絶対位置を読むところだけ**直す
(動かす量は差分なので寄せても変わらない)。1920 幅で 680px 寄った状態でも
ボタンが正しく反応することを、実際にクリックして確かめてある。

### HTML のボタン(`index.html`)

歯車・ホーム・ポーズは窓の角に貼ってあった。`--vt` / `--vr` / `--vb` を
`env.js` が毎回書き込み、CSS 側で足して**板の角**に寄せる。

### 底上げを縦の短さで緩める(`src/env.js`)

```js
export function uiScale(w, h) {
  const floor = Math.min(1.05, h / 520);
  return Math.max(floor, Math.min(w / 380, h / 680, 1.6));
}
```

`h >= 546` では **従来と完全に同じ値**になる(iPhone SE の 553 もこちら側)。
下回ったぶんだけ底上げが緩む。852×393 では 1.05 → 0.756。

### 2行のボタンは、箱が縮んだら字も縮む(`src/render.js`)

呼ぶ側は入りきらないとき箱だけを縮めていて、字は倍率のままだった。
2行が触れずに入る最小の高さ(`40 * UI`)を下回ったぶんだけ、字も同じ率で詰める。

## 3. 直っていることの確かめ方

| 何を | どうやって | 結果 |
|---|---|---|
| 電話が変わっていない | 5機種 × 6画面で、描かれた**文字の座標をすべて突き合わせ** | **30画面すべて一致** |
| 文字が重なっていない | `fillText` を1フレーム乗っ取り、矩形の交差を全組で判定 | 旧にあった4組が消え、増えたものは無し |
| 板からはみ出していない | 同上。板の矩形との比較 | 0件 |
| 指が届く | 1920 / 2560 / 852 / 393 で実際にクリックして状態遷移を確認 | 4つとも OK |
| 落ちていない | 11ビューポート × 13画面で `pageerror` を監視 | 0件 |
| 論理が壊れていない | `node --test test/*.test.js` | **201 件すべて通過** |

計算そのものは `test/layout.test.js` が持っている。とくに
**「電話の縦持ちでは倍率が以前と1ミリも変わらない」**を古い式と突き合わせて固定してあるので、
ここを触れば必ず落ちる。

## 4. やっていないこと

- **横持ちを縦持ちに強制していない。** 面ごとに進行方向が変わる(⬆➡⬇⬅)ので、
  横に広い盤面そのものは成立する。回転をお願いする画面は入れなかった。
- **板の上限 560px の根拠は「電話の幅を大きく超えない」だけ**で、遊び比べて決めた値ではない。
  広すぎると感じたら `STAGE_MAX_W` の1箇所で変わる。
