# 何人まで遊べるのか / いま使っている技術は「本物」なのか

> よく聞かれる2つに、実際のコードを見て答えたもの。

## 0. snap-pair は、このゲームには使っていない

先に事実だけ。**`snap-pair-core` はこのゲームで一度も使われていない。**

- `README.md:64` —「オンライン対戦を有効にする(**Firebase は不要**・約2分・無料)」
- リポジトリ全体を検索して、Firebase への参照は**1件も無い**
- 2人プレイは `src/coop.js` の自前 WebRTC 実装(`RtcTransport`)

`docs/brief.md:156` に「snap-pair のような基盤の横展開」と書いたのは
**将来の事業の話**であって、実装の由来ではない。ここが混ざっていた。

### 「300人つながる」と「3〜4人が限界」は、別のものを数えている

矛盾しているように見えるが、単位が違う。

| | snap-pair | このゲーム |
|---|---|---|
| 1人あたりの更新 | **数秒に1回**(投票した・準備できた) | **毎秒15回**(敵・弾・ベル・ボスの全位置) |
| 1回の大きさ | 数十バイト | **1.5〜3KB** |
| 遅れたら | 気づかない | **死ぬ** |
| 上限の理由 | 同時接続数 | **毎秒の更新回数 × 大きさ × 遅延の許容** |

300は「何人が部屋に**入れるか**」。3〜4は「何人ぶんの世界を**毎秒15回配れるか**」。
snap-pair 自身も `SKILL.md:289` でこう書いている —
*"Avoid per-keystroke or pointer-move writes from every device.
Throttle, debounce, or batch high-frequency input."*
**高頻度の書き込みはするな**、と作者(=あなた)が明記している。
つまり snap-pair は**アクションゲームの同期には最初から向けて作られていない**。
これは欠陥ではなく、狙いが違うだけ。挙手を300人ぶん集めるのは snap-pair が正解で、
弾幕を4人ぶん配るのは別の道具の仕事。

## 0.5 「サーバー」と呼んでいるものが3種類ある

ここが一番の混乱源なので、分けて名前を付ける。

| | ① 出会わせるサーバー | ② snap-pair(Firebase RTDB) | ③ 常駐ゲームサーバー |
|---|---|---|---|
| 何をする | 相手を見つけて繋ぐ | 部屋 + ゆっくり変わる共有状態 | **世界を毎秒60回計算する** |
| 実体 | `api/signal.js`(既にある) | Cloud Functions + RTDB | Node の常駐プロセス + WebSocket |
| 上限 | — | 300人 / 低頻度 | 人数は設計次第 / 高頻度 |
| このゲームでの用途 | **QR・あいことば**(今も使用中) | **使えない** | **「サーバーに移す」= これ** |

前の説明で「サーバーに移す」と言ったのは**③だけ**の話。

**②は③の代わりにならない。** Firebase RTDB は書き込みを保存して配る
データベースであって、ゲームループを持てない。Cloud Functions も
「呼ばれたら返す」形なので、60fps で敵を動かし続けることができない。
さらに RTDB のリージョンに東京が無く、東京↔シンガポールを毎回往復するので、
**いまの P2P より遅くなる**。だから「snap-pair に乗り換えて3人以上」は成立しない。

### iOS だけの話ではない

これも分けておく。**サーバーは、配り方(Web / iOS / Android)と完全に無関係。**

同じ `src/` が3つ全部で動く。③を立てれば、**Web版もiOS版もAndroid版も同時に**
その恩恵を受ける。逆に立てなければ、3つ全部が今のままの P2P で動く。
「iOS用のサーバー」というものは存在しない。

## 1. 3人・4人は「簡単に」はできない。ただし不可能でもない

いまの実装は **1対1に固定**されている。`src/coop.js` の `partner` は
**オブジェクト1個**で、配列ではない。3人目を足すには、ここを配列にして、
接続・位置・スコア・被弾の全経路を人数分に書き換える必要がある。
「設定を変えれば3人」にはならない。

### 接続の形をどうするか(ここが本質)

| 形 | 接続数(4人) | ホストの負担 | 向き不向き |
|---|---|---|---|
| **全員が全員と繋ぐ(メッシュ)** | 6本 | 全員が3本ずつ | 4人でも各自3本。携帯回線だと繋がらない組が出やすい |
| **ホスト中継(スター)** ← いまの延長 | 3本 | **ホスト1台に3本集中** | 3〜4人までは現実的。5人以上でホストが潰れる |
| **常駐サーバー** | 4本 | サーバー | 人数の上限が実質消える。月額が発生する |

いまの作りは「ホストが世界を計算し、他はそれを映す」ので、**スター型の延長が素直**。

### 実際の上限(推定と、その根拠)

スナップショットは約15Hz(`sendSnap` の 66ms)で、敵・弾・ベル・ボスを全部含む。
弾幕時で1回あたりおおよそ 1.5〜3KB。

- 2人: ホストの送信は **約 25〜45 KB/秒**。実測で問題なし(検証済み)
- 3人: **約 50〜90 KB/秒**。携帯回線の上りでも通る見込み
- 4人: **約 75〜135 KB/秒**。上り回線とホスト端末のCPU次第。**ここが現実的な上限**
- 5人以上: ホストが1台のスマホである限り厳しい。常駐サーバーへ移すべき

**結論: スマホだけで安定して遊べるのは3人、頑張って4人。**
5人以上をやるなら、ホストを人の端末から降ろす(=サーバーを立てる)のが正攻法。

### 4人にするなら、実装以外にも要るもの

- ロビーの作り直し(誰が来ているか、誰が準備できたか)
- 残機の扱い(いまは2人でチーム共有。4人で共有だと1人の事故で全員が終わる)
- 画面の情報量(4機ぶんの位置・名前・スコアが出せるか)
- **ホストが落ちたときの引き継ぎ**。2人なら「終わり」で済むが、4人だと理不尽

## 2. 使っている技術は、実際のマルチプレイゲームと同じ系統

これは誇張なしに **同じ考え方**を使えている。

| 技術 | 一般的な名前 | このゲームでの実装 |
|---|---|---|
| ホストが世界の正を持つ | authoritative server / host | 敵・弾・ベル・ボスはホストだけが計算 |
| 状態をまとめて配る | state snapshot | 約15Hzで敵・弾・ベル・ボスを配信 |
| 自分の操作は即反映 | client-side prediction | 自機と自分の弾はローカルで動く(遅延ゼロ) |
| 受信の合間を埋める | interpolation | 15Hzでも滑らかに見えるよう補間 |
| 直接つなぐ | P2P / NAT traversal | WebRTC DataChannel + STUN/TURN |
| 出会わせるだけのサーバー | matchmaking / signalling | `/api/signal`。SDPを5分預かるだけ |

これは *Quake* 以来のネットワークゲームの標準的な作りで、
いまの多くのアクションゲームも同じ骨格を使っている。

### 一方で、商用ゲームにあって我々に無いもの

正直に並べると、まだこれだけ差がある。

| 無いもの | 何が起きるか |
|---|---|
| **巻き戻し補正(rollback / reconciliation)** | ゲスト側の「当たった/当たってない」がホストとズレたとき、静かに直せない |
| **差分圧縮(delta compression)** | 毎回まるごと送っている。人数が増えると効いてくる |
| **遅延補償(lag compensation)** | 相手の回線が悪いと、相手にとって不利なまま |
| **常駐サーバー** | ホストが落ちると世界が消える |
| **チート対策** | ホストを信頼しているので、ホストが改造すると何でもできる |

順番としては、**3〜4人に広げるより先に、常駐サーバーへ移す**方が筋がいい。
サーバーがあれば人数も、ホスト落ちも、チートも、まとめて解ける。

## 2.5 「サーバーに移す」とは何か — QRコードは無くならない

上で「常駐サーバーへ移すべき」と何度か書いたが、これは**QRコードをやめる話ではない**。
混同されやすいので、ここに分けて書いておく。

**サーバーは既に1つある。** `api/signal.js` がそれで、役割は「二人を引き合わせる」だけ。
あいことばごとに SDP(接続情報)を5分だけ預かり、繋がった瞬間に用済みになる。
QRコード(`Coop.inviteUrl()` → `?join=CODE`)も、6文字のあいことばも、招待リンクも、
**全部この層のもの**。

つまり、いまのコードには2つの層がある。

| 層 | 役割 | いまの担当 | 「サーバーに移す」と |
|---|---|---|---|
| **出会う層** | 相手を見つけて繋ぐ | `api/signal.js` + QR/あいことば | **変わらない** |
| **世界を計算する層** | 敵・弾・ベル・ボスを動かす | **ホスト側プレイヤーのスマホ** | ここだけが常駐サーバーに移る |

移すのは下の行だけ。上の行はそのまま残る。
遊ぶ人から見た手順(QRをかざす / あいことばを入れる)は**1ミリも変わらない**。

### なぜ移すと良くなるのか

いまは `src/engine.js` のあちこちに `isGuest()` の分岐があり、
**ホストは敵もベルもボスHPも自分の端末で計算している**。
その結果:

- **ホストの遅延はゼロ、ゲストだけが遅延を背負う。** 対等ではない
- **ホストが抜けると世界が消える。** 途中でアプリを閉じられたら終わり
- 直接つながらない組が出る(以前見た「直接つながれませんでした」がこれ)
- ホストを信頼しているので、ホストが改造すれば何でもできる
- ホスト1台が上限なので、人数を増やすとホストが潰れる

サーバーが世界を計算すれば、この5つが**まとめて**消える。二人とも同じだけ遅い、が公平。

### 代わりに失うもの

- `docs/brief.md` に書いた原則「サーバーはゲーム中の経路に入れない」を**自分で破ることになる**
- 月額が発生する(いまは KV が5分だけ動くので実質ゼロ)
- 往復が1回増える。P2P で直接つながっている組は、いまより遅くなる

**判断:** 2人で遊ぶ限り、いまの P2P のほうが速くて安くて正しい。
移すべきなのは **3人以上をやると決めたとき**か、
**「直接つながれませんでした」が実際のテスターから頻繁に出たとき**。
どちらもまだ起きていないので、今は移さない。

## 2.6 実装するとしたら — 「移す」ではなく「足す」

サーバーを立てると決めた場合の、実際の手順と労力。
調べた結果、**思っていたより条件は良い**。

### すでに揃っているもの(実測)

- **`src/engine.js` に DOM 参照が 0 件。** `document` / `window` / `canvas` / `ctx`
  を検索してヒットしない。**ゲームロジックは既にヘッドレスで動く形をしている**
- **`src/coop.js` は transport を差し替えられる。** `RtcTransport` と
  `MockTransport` の2実装が既にあり、`send` / `dispose` / `update` / `open` の
  同じ形をしている。**3つ目として `WsTransport` を足せる**
- **同期プロトコルはそのまま使える。** ホスト権威・15Hzスナップショット・
  補間は、ホストが「人の端末」から「サーバー」に変わっても中身は同じ

### 順番(後戻りしない順)

| | やること | 労力 | 今すぐできるか |
|---|---|---|---|
| 1 | **engine を Node で走らせるテストを書く**。1ステージを最後まで自動プレイさせて、敵もボスも動くことを確かめる | 小 | **できる。無料。0円** |
| 2 | `WsTransport` を足す(P2P と**選択制**、置き換えではない) | 中(約120行) | できる |
| 3 | サーバーを立てて engine を載せる | 中〜大 | 月額が発生する |
| 4 | `partner` を配列にして3〜4人へ | 大 | 3 の後 |

**1は今すぐやる価値がある。** サーバーを立てるか決める前に、
「ゲームロジックが画面なしで正しく走る」ことが証明でき、
それ自体がテストとして永久に効く。**サーバーをやめても無駄にならない唯一の段**。

### 大事な但し書き — 2人プレイは**遅くなる**

③を経由すると往復が1回増える。いま直接つながれている2人にとっては、
サーバーは**改悪**になる。だから「移す」のではなく、
**2人=P2P / 3人以上=サーバー、と使い分ける**のが正しい形。
`transport` が既に差し替え可能なので、この分岐は自然に書ける。

## 3. iOS と Android を同時に作る方法

Swift や Kotlin を書かずに両方を出す道はいくつかある。
**この作品(Canvas2D の JavaScript, 約6,000行)にとっての向き不向き**で並べる。

| やり方 | 書き直し | 速度の心配 | 向き |
|---|---|---|---|
| **Capacitor** (WebView + ネイティブ橋渡し) | **ほぼゼロ** | **無い**(実測60fps) | ◎ いまのコードがそのまま動く |
| **React Native** | 全部 | 2Dなら可 | △ Canvas主体だと相性が悪い |
| **Flutter** | 全部(Dart) | 良い | △ 資産を捨てることになる |
| **Unity / Godot** | 全部 | 非常に良い | △ このゲームには過剰 |

### 「ネイティブで書かないと悪くなるのか?」→ 速度は問題にならない

このゲームは **Canvas2D で弾50発・60fps** が出ている。
WebView でも同じ描画エンジンなので、**性能面でネイティブに劣る心配は要らない**。

本当に差が出るのはそこではなく、次の3つ。

1. **審査(Apple 4.2)** — 「サイトを包んだだけ」に見えると落ちる。
   Game Center・課金・触覚(バイブ)・プッシュ・完全オフラインを実装すれば通る例は多い。
   Capacitor はこれらのAPIを持っているので、**書き直さずに「ネイティブらしさ」を足せる**。
2. **手触りの細部** — 触覚フィードバック、消音スイッチの尊重、電話着信での中断復帰。
   どれも Capacitor のプラグインで足せる。
3. **起動速度** — アプリに同梱すればネットワーク待ちが消えるので、むしろ今より速くなる。

**推奨: Capacitor。** いまの資産を捨てず、Android を先に出し、
iOS は触覚・Game Center・課金を足してから出す。
