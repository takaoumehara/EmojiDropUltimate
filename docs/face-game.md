## 1. これは何か

`face.html`。カメラで顔を撮り、**落ちてくる的に描かれた表情を作ると的が壊れる**。
60秒で終わり、**命中数・平均反応時間・誤爆数**が出る。

**ゲームではなく実験装置。** 確かめたい問いは引き継ぎ文書のとおり1つだけ。

> 顔で操作するのは、10秒で飽きる珍しさではなく、もう一回やりたくなる操作なのか。

## 2. いちばん大きな設計判断 — タップ経路を先に入れた

引き継ぎ文書は「HTML 1枚、カメラで顔を試す」と書いている。**実装では、同じ画面に
タップでも遊べる経路を入れた。** 理由は4つあり、どれも実験装置の精度に直結する。

### 2-1. これがないと、測った数字の意味が確定しない

文書が測ろうとしている「反応の遅れ（顔を作ってから弾けるまで）」は、
**ブラウザの中からは原理的に測れない。**「顔を作った瞬間」を知る手段が
カメラしかなく、そのカメラの遅れこそが測りたいものだからである。
自分の遅れを自分で測ることはできない。

実際に測れるのは「**的が壊せる状態になってから、壊れるまで**」で、これは

```
人間の反応時間 ＋ 表情を作る筋肉の時間 ＋ カメラと推論とフィルタの遅れ
```

の合計になる。3つが混ざった数字を見て「200ms 超えたから離散操作に振り切る」と
判断するのは危うい。**同じ人が、同じ的を、同じ日にタップでも撃てば、
差分がカメラ由来の遅れになる。** 引き算で出せる。

だから結果画面には**タップ版との差**を出す。文書の分岐条件
「200ms 超なら離散的な操作に振り切る」は、この差に対して適用すべき数字である。

### 2-2. 手触りのバグと入力のバグを、同時には切り分けられない

的が壊せなくて気持ち悪い時、原因は「的の落ち方が悪い」のか「しきい値が高い」のか
「遅延」なのか。タップ版が気持ちよければ、**残りは全部入力層の問題だと確定する。**

### 2-3. プレイテストの回数が出せる

顎は30〜60秒で疲れる。**顔経路は1人あたり数回しか試せない。**
タップなら何十回でも回せるので、的の落ち方・帯の広さ・出題間隔の調整は
タップ側で先に終わらせられる。

### 2-4. カメラを許可しない人・使えない人の経路になる

後付けが最も難しい部分で、最初から二重に作れば実質タダで手に入る。

### 代償（自覚して払う）

- HTML 1枚のつもりが**1画面＋6ファイル**になった。30分では終わらない
- タップ版で先に楽しさを確認すると、「顔だから面白い」の検証が甘くなる危険がある
  → **結果画面で両方の数字を並べる**ことで、そこは可視化する

## 3. 外部依存の扱い

既存ゲームの第1原則は「外部依存を足さない」。**この原則は `index.html` のもので、
`face.html` には適用しない**（引き継ぎ文書 §8 の判断と同じ）。
ただし線は引く。

| 経路 | 外部依存 | オフライン |
|---|---|---|
| **タップ** | **ゼロ** | **動く** |
| 顔 | MediaPipe（CDN） | 動かない |

**MediaPipe はカメラの許可が下りた後に初めて読み込む。**
タップで遊ぶ人のところには 1バイトも降ってこない。

### ダウンロード量（実測）

ここが引き継ぎ文書に数字が入っていなかった箇所で、**実測したら想定よりずっと重い。**

| 何 | 大きさ |
|---|---|
| `face_landmarker.task`（float16 v1） | **3,758,596 バイト ≒ 3.6MB**（実測。文書の数字と一致） |
| `vision_wasm_internal.wasm` | **12MB**（実測） |
| `vision_bundle.mjs` | 152KB（実測） |
| **合計** | **およそ 15.6MB** |

`@mediapipe/tasks-vision@1.0.1` を npm から実際に取得して測った。

**モバイルの初期ロードは 2MB 以下が安全とされる目安なので、その8倍近い。**
これは設計で消せる量ではない。引き受け方は3つで、いま採ったのは①。

1. **許可の後にだけ読む**（採用）。タップの人には降らない
2. 自分のドメインに wasm を置いて gzip/brotli で配る（wasm は圧縮が効く）。**②に進む時に検討**
3. 顔検出だけの軽いモデルに落とす → 52個の blendshape が消えるので、この企画では選べない

**「①が面白かったらスマホで試す」段階で、回線が遅い場所での初回起動を必ず測ること。**
ここが実は「面白いかどうか」より先に人を落とす可能性がある。

### 置き場所は差し替えられるようにした

`face.html` の `<meta name="mediapipe-base">` / `<meta name="face-model">` を埋めると、
自分のドメインから配れる（既存の `coop-relay` と同じ作法）。空なら CDN。

②で必要になるのが分かっているのと、**CDN が塞がれている回線が実在する**ため。
実際にこのリポジトリでの検証中、サンドボックスの経路で `cdn.jsdelivr.net` が
`ERR_TUNNEL_CONNECTION_FAILED` になった。会社・学校・国のネットワークで同じことが起きる。
その時「動かないゲーム」になるか「置き場所を変えれば動く」かは、後から足すと面倒な差。

## 4. MediaPipe の API（記憶ではなく実物で確認した）

引き継ぎ文書 §6 に「API の正確な名前とバージョンは実装時に公式で確認すること
（ここは記憶ベース）」とあるので、**パッケージ本体とモデル本体を取得して確認した。**

- パッケージ: `@mediapipe/tasks-vision`、**最新は 1.0.1**（実測）
- 生成: `FilesetResolver.forVisionTasks(basePath)` → `FaceLandmarker.createFromOptions(fileset, opts)`
- オプション: `baseOptions.modelAssetPath` / `baseOptions.delegate` / `runningMode: 'VIDEO'` /
  `outputFaceBlendshapes: true` / `numFaces`
- 毎フレーム: **`detectForVideo(video, timestampMs)`**（同期で返る）
- 返り値: `{ faceLandmarks, faceBlendshapes: [{ categories: [{ categoryName, score }] }], ... }`

`face_landmarker.task` は zip で、中の `face_blendshapes.tflite` に名前が入っている。

## 5. 何を出題するか

### 5-1. 5つのうち3つしか使わない

引き継ぎ文書は 😮😊😲😗😑 の5つを挙げている。**実験装置では 😮😊😲 の3つだけ出題する。**

| | 使う | blendshape | 理由 |
|---|---|---|---|
| 😮 開口 | **出題する** | `jawOpen` | 顔で最も信号が大きい。文書のとおり最初の一本 |
| 😊 口角 | **出題する** | `mouthSmileLeft/Right` の平均 | 開口と混ざりにくく、作りやすい |
| 😲 眉上げ | **出題する** | `browInnerUp` | 口と完全に別部位。「部位が散る」の検証になる |
| 😗 口すぼめ | 出題しない | `mouthPucker` | 開口・笑顔と同じ口。誤爆の温床。**背後で測るだけ** |
| 😑 閉眼 | 出題しない | `eyeBlinkLeft/Right` | 画面を見ていないと成立しない。文書 §3 の「目を連続操作に使わない」に触れる |

**一度に渡す新しい概念は4つが上限**なので、3つを**1ラウンドに1つずつ**増やす。
5つ同時に出すと、面白いかどうかではなく覚えられるかどうかを測ることになる。

### 5-2. 出題しない2つも、裏では測る

😗 と 😑 は**出題しないが、しきい値の越え方は60秒間ずっと記録する。**
プレイ中に何回勝手に反応したかが、そのままプレイ時間ゼロで手に入る。
文書の「誤爆が多い表情はゲームで使わない」の判断材料はこれで揃う。

## 6. 実験装置の中身

### 6-1. 60秒の組み立て

```
0〜5秒    カメラが立ち上がる。顔が見つかる。何もしない状態の値を測る（安静基準）
5〜17秒   ラウンド1  😮 だけ
17〜21秒  休み（数字だけ出る。何もしないのが正解）
21〜33秒  ラウンド2  😮 ＋ 😊
33〜37秒  休み
37〜49秒  ラウンド3  😮 ＋ 😊 ＋ 😲
49〜53秒  休み
53〜65秒  ラウンド4  3つ全部・間隔を詰める
          → 結果
```

- **休みは合計12秒 ≒ 20%。** 顎を使う入力の休息比率の下限。減らさない
- 休みは無操作が正解。ここで数字を見せるので、休憩が退屈にならない
- 1プレイ 65秒。**顎が連続で持つのは30〜60秒**なので、これが上限に近い

### 6-2. 的の壊し方 — 線ではなく帯

**遅延を「失敗の原因」ではなく「点数の差」に変える。**

的は落ちてくる。画面のある高さから下の**帯**の中にいる間だけ壊せる。
帯は 1.5秒ぶんの高さがあり、**帯に入る 800ms 前から的が光り始める**（予告）。

- 帯の中心に近いほど点が高い。**遅れは点差になるだけで、失敗にはならない**
- 「タイミングが合っていたのに Miss」が起きない。±180ms より狭い判定はしない
- 次の的までは最低 700ms 空ける。**前の表情から顔が戻りきる時間**

引き継ぎ文書の「遅延が問題にならない」は、この形にして初めて本当になる。
落下の締切がそのまま判定線だと、100ms は締切から 100ms を引くのと同じで、
ちゃんと遅延の分だけ不利になってしまう。

### 6-3. 違う表情を作った時、何が起きるか

**ここが実験装置でいちばん壊れやすい所。**

😮 の的が出ている時に笑ってしまった場合、罰を与えてはいけない。人は遊んでいると
勝手に笑う。**自分のせいではないことで損をした瞬間に、人はやめる。**

採った形:

- **違う表情を作っても、減点もミスもしない**
- ただし**違う表情を作っている間は、正しい表情でも壊せない**
  （実際に、口を開けながら同時に笑うことはできない。画面の中の嘘ではない）
- 何が邪魔しているかは、**そのメーターが光ることで見える**。文章では説明しない
- そして**その全部を誤爆として記録する**

これで「全部の顔を同時に作れば勝てる」が成立せず、かつ理不尽が生まれない。

### 6-4. 疲労を、感想ではなく数字にする

文書は「何秒で顎が疲れるか」を**いちばん大事**としている。主観では60秒後に
「まあまあ疲れた」しか残らないので、**1発ごとに、その時の最大振幅を記録する。**

前半20発の平均と後半20発の平均を比べれば、振幅の低下率が出る。
これが疲労の代理指標になる。

**ここに罠があって、実装で明示的に分けた。** 疲れると動作が小さくなるので、
遊びやすさのためにはしきい値を下げて追従させたい。しかしそれをやると、
**測ろうとしている疲労そのものが隠れる。**

→ **しきい値は追従させる（遊べる）。記録は生の振幅で取る（測れる）。**
片方だけにすると、遊べないか、測れないかのどちらかになる。

### 6-5. 顔が見えなくなった時

顔は必ず外れる。振り向く、暗い、逆光、眼鏡の反射、子供が手を振る。

| 状況 | どうするか |
|---|---|
| 数フレーム消えた | 直前の値を保つ。0 に落とすと入力が暴れて誤爆する |
| 0.5秒以上消えた | **まず進行を 0.35倍に落とす**。多くはここで戻る |
| さらに続く | 止める。画面の縁の色で伝える（文章を出さない）。戻ったら自動で再開 |
| 複数人映った | 使っている顔に枠を出す。黙って切り替えると原因不明の暴走に見える |

**見えていない間にゲームを進めない。** 操作できないのに失敗するのは、
理不尽の中で最も強い種類。

## 7. 個人差の吸収 — 設定画面を作らない

口の大きさ・開く量・眉の上がり方は個人差が大きい。**作者の値を定数にすると、
他人には反応しないゲームになる。** かといって「口を最大に開けてください」を
初手に置くのは、初見の摩擦として大きすぎる。

遊びの中で測る。

```
0〜5秒     何もしていない値 → 各表情の下限
ラウンド1の最初の3発  的が大きくゆっくり落ちてくる（しきい値が低い）
                     ここで出た値が上限になる
以降       上限を上回ったら広げる。下回っても、ゆっくりしか下げない
```

- 上限が下限に近すぎたら（＝何もしなかった人）、安全な既定値へ落とす。
  そうしないとゼロ除算か、極端に過敏になる
- ラウンド1の最初の3発は「餌」であって計測画面ではない。**測っている間もゲームは進む**

## 8. しきい値はヒステリシスで持つ

1つのしきい値で「作った／作っていない」を判定すると、境界で毎フレーム反転する。
推定値は常に揺れているので、必ず起きる。

**作る時のしきい値と、やめる時のしきい値を分ける。**
差は正規化値で 0.2。**差をゼロにすると「たまに反応しない／勝手に反応する」になる。**
加えて最小保持 90ms。これはそのまま入力遅延として乗るので、これ以上は増やさない。

揺れは One Euro Filter で取る。ゆっくりの時は強くかけ、速い時は弱める。
**調整は必ず片方ずつ。** 同時に動かすと、どちらが効いているか永遠に分からない。

### beta の既定値 0.007 をそのまま使うと、100ms 損する（実測）

One Euro の教科書的な初期値 `beta = 0.007` は**座標（ピクセルやメートル）を平滑化する
前提の値**で、微分の大きさが数百〜数千になることを想定している。
こちらの入力は 0〜1 に正規化済みなので微分はせいぜい 1〜10 にしかならず、
`beta * |dx|` がほとんど効かない。**つまり「速く動いた時に弱める」が働かない。**

実測（1/60秒刻み、0.02 → 0.9 の立ち上がりが `active` になるまで）:

| beta | 立ち上がり | 静止時の震え |
|---|---|---|
| 0.007（教科書の値） | **233ms** | 0.058 |
| 0.15 | 167ms | 0.058 |
| **0.8（採用）** | **133ms** | 0.059 |
| 3.0 | 117ms | 0.068 |

0.8 で **100ms 縮み、震えは実質増えない**。それ以上上げても 117ms（最小保持 90ms の床）に
当たってほぼ縮まず、震えだけ増える。

**この 100ms は、そのまま結果画面の「反応の時間」に乗っていた。**
0.007 のままだと、カメラのせいではない遅れを 100ms 分カメラの数字に混ぜたまま
「200ms を超えたから離散操作に振り切る」と判断することになっていた。

## 9. カメラの扱い（ここは譲らない）

- **推論は端末の中だけで完結する。映像はどこにも送らない。** 子供の顔を扱う以上、ここが要
- **許可を求める前に、何に使うかを見せる。** いきなり `getUserMedia` を呼ぶと拒否される
- **裏でフレームを溜めない。** 共有機能のためでも、本人が知らない保存は裏切りになる
- **カメラが動いていることを画面に出す。** ブラウザのインジケータ任せにしない
- **拒否は失敗ではなく分岐。** 拒否したらタップ経路へ行く。そこで詰まない
- **`getUserMedia` は HTTPS が要る**（`localhost` は可）。スマホ実機の時点で必須

顔の特徴量は地域によって生体情報として通常の個人情報より厳しく扱われる。
**保存・送信を始める時が来たら、その前に適用される規制を確認すること**（ここは法的助言ではない）。

## 11. ファイル構成と、SW の巻き添え事故

```
face.html                  1画面。ここだけ見れば遊べる
src/face/signal.js         入力の契約・ヒステリシス・One Euro・キャリブレーション
src/face/facesource.js     MediaPipe（許可後に遅延読み込み）
src/face/tapsource.js      タップ経路
src/face/metrics.js        計測と集計
src/face/game.js           60秒の実験装置
src/face/audio.js          効果音（Web Audio、外部依存なし）
src/face/main.js           画面遷移
```

### なぜ `src/face/` の下なのか（重要）

`sw.js:92` の `isSrcModule()` は **`/src/` で始まり `.js` で終わる**ものだけを
network-first にしている。それ以外の同一オリジンのファイルは **cache-first**。

つまり **`/face/main.js` のような置き方をすると、一度読んだ端末は
新しいコードを永久に受け取らない。** 実験装置は毎日直すものなので、これは致命的。

`face.html` 自身はナビゲーションなので network-first で問題ないが、
**オフライン時に `caches.match('/index.html')` へ落ちて別のゲームが出る**ので、
`face.html` を precache に足し、`VERSION` を上げた。

## 12. 検証

**カメラ入力は、作った本人の環境で完璧に動き、他人の環境で動かない。**
以下は全部、作者以外で試す。

| 見ること | 合格 |
|---|---|
| **うなずく・首を振る** | それだけで口が開いたことにならない |
| **距離を変える** | 40cm と 120cm で同じ動作が同じ値になる |
| **暗さ・逆光** | 遅延が増えることと、ロスト時の挙動が §6-5 のとおり |
| **眼鏡・マスク・帽子** | 落ちる条件を把握している（直せなくてもよい。把握していないのは別問題） |
| **作者以外3人** | キャリブレーションが成立し、全員が反応する |
| **3分連続** | 疲労で入力が小さくなっても遊べる。同時に発熱を見る |
| **遅延の実測** | **画面と自分の顔を同時に60fps以上で撮ってフレームを数える。推測しない** |
| **タップとの比較** | 同じ人が両方遊び、どちらも「同じゲーム」だと言う |
| **回線が遅い場所での初回起動** | 15.6MB が降りきるまでに何が見えているか（§3） |

### ①の判断基準（文書 §5 の分岐をそのまま）

| 測ったもの | 悪かったら |
|---|---|
| **タップとの反応時間の差** が 200ms 超 | 離散操作に振り切る（＝表情マッチ確定、口砲は捨てる） |
| **誤爆**が多い表情 | ゲームで使わない。しきい値とヒステリシスで対処 |
| **何秒で顎が疲れるか** | 40秒で疲れるなら1ステージ30秒。**ここでゲームの長さと休憩が全部決まる** |

**「面白くない」と分かって終わる可能性は十分ある。それは失敗ではなく、
いちばん安く答えが出たということ。**

## 12-b. いま何が確認できていて、何が確認できていないか

**「コードが書けている」と「遊べる」は別**なので分けて書く（`docs/status.md` と同じ作法）。

### 実際に走らせて確認したもの

| | どうやって |
|---|---|
| 画面なしのテスト **39件** | `node --test test/face.test.js`（既存201件と合わせて240件が通る） |
| ゆびの経路が最後まで通る | Chromium で65秒プレイ。結果画面まで出る。JSエラーなし |
| **カメラの経路が最後まで通る** | 偽カメラ + MediaPipe をローカル配信。3秒で起動し、遊ぶ画面に入る |
| **顔が見えない間、進行が止まる** | 偽カメラ（顔なし）で7秒放置 → 時計が **65 のまま動かない**。画面の縁が赤 |
| GPU が無い端末での CPU 退避 | ヘッドレスには GPU が無いので、実際に CPU 側の経路が走った |
| モデルとパッケージの実在 | npm と Google のサーバーから実際に取得。blendshape 52個をモデル本体から抽出 |
| 画面の要素とコードの対応 | `main.js` が触る id が全部 `face.html` にあることをテストで固定 |
| 鏡がメーターに被らないこと | 実座標で確認（最初は**被っていた**。3つ目のメーターが隠れていた） |

### 確認できていないもの（ここは人間が要る）

| | なぜできないか |
|---|---|
| **本物の顔で反応するか** | 偽カメラには顔が無い。**カメラの前に人が座らないと分からない** |
| **実際の遅延** | 画面と顔を60fps以上で同時に撮ってフレームを数えるしかない。推測しない |
| **何秒で顎が疲れるか** | 顎が要る |
| **面白いかどうか** | ①の問いそのもの。これを測るために作った |
| 距離・明るさ・眼鏡・複数人 | 全部 §12 のとおり、人と部屋が要る |
| スマホの実機 | HTTPS が要る。②の段階 |

**つまり、この実装で答えが出たものは1つも無い。出せる状態にしただけ。**
それが①の正しい成果物なので、これでよい。
